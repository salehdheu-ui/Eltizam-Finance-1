# الانتقال إلى سجل مالي دقيق

## الهدف

إضافة سجل حركات مالي قابل لإعادة الحساب والتدقيق دون كسر الجداول الحالية أو تغيير تجربة المستخدم دفعة واحدة.

## القرار الانتقالي

سيبقى جدول `transactions` مصدراً متوافقاً مع واجهة التطبيق في المرحلة الأولى، بينما يضاف جدول `ledger_entries` كسجل مالي دقيق لكل حركة مرتبطة بمحفظة. كل معاملة مستخدم تنشئ إدخال ledger واحداً لكل محفظة تتأثر بها؛ لذلك ينشئ التحويل إدخالين، واحداً مديناً للمحفظة المصدر وواحداً دائناً للمحفظة المستقبلة.

## الحقول الأساسية

| الحقل | الغرض |
|---|---|
| `user_id` | عزل بيانات المستخدم |
| `wallet_id` | المحفظة المتأثرة |
| `transaction_id` | الرجوع إلى الحركة الظاهرة للمستخدم |
| `amount` | قيمة عشرية دقيقة محفوظة كسلسلة `numeric(20,3)` |
| `direction` | `credit` أو `debit` |
| `source` | `manual`, `bank`, `recurring`, `adjustment`, أو `transfer` |
| `currency` | العملة في لحظة التسجيل، افتراضياً `OMR` |
| `external_id` | معرف المصدر الخارجي عند توفره |
| `idempotency_key` | منع إنشاء نفس الحركة مرتين عند إعادة المحاولة |
| `occurred_at` | وقت حدوث الحركة، مستقلاً عن وقت إدخالها |
| `reversed_by_id` | ربط الحركة بحركتها العكسية مستقبلاً |

## قواعد الاتساق

أولاً، لا يُكتب ledger entry دون معاملة مرتبطة، إلا في الحالات التي يقرر فيها النظام لاحقاً دعم قيود مستقلة. ثانياً، لا يُسمح بمبلغ يساوي صفراً أو سالباً. ثالثاً، تُنشأ المعاملة والـ ledger entry وتحديث الرصيد داخل PostgreSQL transaction واحدة. رابعاً، لا تحذف الحركة المالية في الإصدار اللاحق؛ تنشأ حركة عكسية مرتبطة بها.

## خطة الترحيل

1. إنشاء الجدول والفهارس دون تغيير القراءة الحالية.
2. تعبئة ledger من كل `transactions` الموجودة مع `source=manual` مبدئياً، ثم تحسين المصدر من أحداث البنك والدخل المتكرر حيث يمكن إثباته.
3. مقارنة مجموع ledger مع أرصدة المحافظ الحالية وإنتاج تقرير فروقات.
4. جعل الكتابات الجديدة تنشئ ledger entry داخل نفس transaction.
5. تحويل تقارير الرصيد تدريجياً إلى ledger بعد نجاح المقارنة.
6. إبقاء `wallets.balance` كـ cache مؤقت مع مهمة تحقق دورية.

## خارج نطاق الدفعة الحالية

تعدد العملات الفعلي، المحاسبة مزدوجة القيد الكاملة، الضرائب، التسويات البنكية المتقدمة، وإعادة بناء التاريخ المالي دون موافقة المستخدم. هذه موضوعات لاحقة بعد نجاح الانتقال الأساسي.
