# خطة مهام الدفعة P2 لمنصة التزام

## الهدف

توسيع أساس P1 إلى منصة مالية قابلة للاستعادة والمراجعة والتوسع، دون كسر البيانات الحالية أو السماح باستيراد غير قابل للتراجع. ستبدأ P2 بميزات الثقة والتحكم في البيانات، ثم تنتقل إلى القراءة من ledger والتعدد النقدي ومزامنة البنك.

> قاعدة التنفيذ: كل مهمة مالية يجب أن تكون قابلة للتراجع، مرتبطة بالمستخدم الحالي، محمية باختبار، ولا تغيّر `main` مباشرة.

## ترتيب التنفيذ

| المعرّف | المهمة | الأولوية | يعتمد على | مخرج المهمة |
|---|---|---:|---|---|
| P2-IMP-01 | تعريف عقد ملف التصدير v1 والتحقق الصارم منه | حرجة | P1 export | validator مشترك مع رسائل أخطاء عربية |
| P2-IMP-02 | بناء معاينة الاستيراد مع خرائط المعرفات والبصمات | حرجة | P2-IMP-01 | تقرير new/duplicate/conflict/error دون كتابة |
| P2-IMP-03 | تنفيذ commit للاستيراد داخل transaction | حرجة | P2-IMP-02 | استيراد قابل للتراجع مع سجل عملية |
| P2-IMP-04 | إضافة واجهة رفع/معاينة/تأكيد الاستيراد | عالية | P2-IMP-03 | شاشة استيراد آمنة في الإعدادات |
| P2-REV-01 | توحيد حالات المراجعة البنكية وفجوات الرصيد | عالية | P1 bank inbox | API موحد لحالات pending/gap/duplicate |
| P2-REV-02 | بناء مركز المراجعة والتسوية | عالية | P2-REV-01 | شاشة قرارات مع سبب وإجراء واضح |
| P2-REV-03 | إضافة اختبارات انتقال الحالة والتوفيق | عالية | P2-REV-02 | اختبارات قبول لكل قرار مالي |
| P2-LED-01 | إضافة استعلامات ledger للتقارير والأرصدة | حرجة | P1 ledger | مصدر قراءة موحد مع fallback مراقب |
| P2-LED-02 | تنفيذ إعادة حساب الرصيد والمقارنة | حرجة | P2-LED-01 | تقرير فرق لكل محفظة |
| P2-LED-03 | تحويل dashboard/reports تدريجياً إلى ledger | عالية | P2-LED-02 | feature flag وقياس تطابق النتائج |
| P2-FX-01 | إضافة جدول العملات وأسعار الصرف المؤرخة | عالية | P2-LED-01 | سعر صرف محفوظ مع مصدر ووقت |
| P2-FX-02 | إضافة عملة لكل محفظة وحركة وميزانية | عالية | P2-FX-01 | لا يوجد تحويل ضمني أو فقد دقة |
| P2-FX-03 | واجهة عرض العملة الأساسية والتحويل | متوسطة | P2-FX-02 | عرض واضح للمبلغ الأصلي والمحوّل |
| P2-SYNC-01 | نموذج محاولات المزامنة وحالتها | متوسطة | P1 bank inbox | سجل attempt وbackoff وlast error |
| P2-SYNC-02 | إعادة محاولة آمنة ومحدودة للمزامنة | متوسطة | P2-SYNC-01 | retry لا يكرر الحركات |
| P2-SYNC-03 | مؤشرات تشغيل ومركز صحة التكاملات | متوسطة | P2-SYNC-02 | success rate وlast sync وpending |

## P2-IMP: الاستيراد الآمن

### P2-IMP-01 — عقد الملف والتحقق

يجب أن يحتوي الملف على `exportVersion`, `exportedAt`, وكيانات مصفوفية معروفة. يمنع validator الحقول الزائدة الحساسة، يحدد حجماً أقصى للملف، ويتحقق من أنواع المبالغ والتواريخ والعملة. لا يعتمد الاستيراد على المعرفات الرقمية القديمة باعتبارها معرفات داخلية صالحة.

### P2-IMP-02 — المعاينة

تُنشأ بصمة مستقرة لكل كيان. بالنسبة للمعاملات تعتمد البصمة على نوع الحركة والمبلغ والمحفظة المنطقية والملاحظة والتاريخ ومفتاح المصدر إن وجد. تعرض المعاينة عدد السجلات الجديدة والمكررة والمتعارضة، ولا تنفذ أي كتابة.

### P2-IMP-03 — التأكيد والتراجع

تُحفظ عملية الاستيراد بمعرّف دفعة، وتُنفذ داخل transaction أو آلية تعويض واضحة. تُنشأ الخرائط من معرفات الملف إلى معرفات قاعدة البيانات، وتُربط الحركات بالـ ledger عبر مصدر `import`. إعادة رفع نفس الملف لا تنشئ نسخاً ثانية.

## P2-REV: مركز المراجعة

يُجمع في المركز كل ما يحتاج قراراً: أحداث بنكية بحالة `review`, فجوات الرصيد، معاملات مكررة محتملة، أحداث بلا محفظة، وتصحيحات معلقة. كل قرار يجب أن يسجل الفاعل والوقت والسبب والنتيجة، مع منع الانتقال غير الصالح مثل اعتماد حدث محذوف أو عكس حركة عكسية.

## P2-LED: القراءة من ledger

يتم أولاً تنفيذ استعلامات تجميع مستقلة من ledger، ثم مقارنة الرصيد المحسوب مع `wallets.balance`. لا يُزال الحقل القديم مباشرة؛ يبقى كـ cache إلى أن تثبت المطابقة على staging والإنتاج. أي فرق يظهر للمستخدم الداخلي مع request ID وسجل تدقيق.

## P2-FX: التعدد النقدي

لا يجوز تفسير مبلغ بلا عملة. تضاف عملة أصلية للحركة وسعر صرف مؤرخ عند الحاجة فقط. تحفظ القيمة الأصلية والقيمة الأساسية منفصلتين، ويمنع تعديل سعر صرف تاريخي بعد استخدامه دون سجل تصحيح. تنفيذ العملات سيكون بعد نجاح استعلامات ledger حتى لا تتضاعف مصادر الحقيقة.

## P2-SYNC: المزامنة

كل محاولة مزامنة يجب أن تحمل `attemptId`, `startedAt`, `finishedAt`, `status`, `retryCount`, و`lastError` منقحاً. إعادة المحاولة تستخدم نفس مفاتيح idempotency، وتمنع أكثر من محاولة فعالة للتكامل نفسه، وتعرض آخر مزامنة للمستخدم.

## معايير القبول العامة

| المجال | معيار القبول |
|---|---|
| سلامة البيانات | فشل أي مرحلة لا يترك بيانات جزئية أو دفعة غير معروفة |
| منع التكرار | تكرار نفس الملف أو المزامنة لا ينشئ حركة ثانية |
| العزل | لا يستطيع المستخدم معاينة أو استيراد أو مراجعة بيانات مستخدم آخر |
| التدقيق | كل اعتماد أو تصحيح أو استيراد له actor وtimestamp وreason |
| الدقة | كل مبلغ يمر عبر تحقق رقمي واضح ولا يعتمد على floating point غير المنضبط |
| القابلية للتشغيل | كل فشل يعيد request ID ورسالة عامة وتفصيلاً داخلياً منقحاً |
| الاختبارات | unit tests للقواعد وPostgreSQL integration tests للـ transaction والتزامن |

## ما لن يدخل في P2 الأولى

لن تشمل الدفعة الأولى من P2 مشاركة الحسابات العائلية، الاشتراكات، تكاملات بنكية جديدة غير موثقة، أو ذكاء اصطناعي يتخذ قراراً مالياً تلقائياً. تؤجل هذه البنود حتى اكتمال الاستيراد، مركز المراجعة، ومطابقة ledger.

## أول إصدار برمجي مقترح

يبدأ التنفيذ الفعلي بالمهام `P2-IMP-01` إلى `P2-IMP-04`، ثم `P2-REV-01` و`P2-REV-02`. بعد نجاحهما يبدأ `P2-LED-01`. بهذه الطريقة يحصل المستخدم أولاً على التحكم في بياناته والمراجعة المالية، قبل توسيع الحسابات إلى العملات والتكاملات.
