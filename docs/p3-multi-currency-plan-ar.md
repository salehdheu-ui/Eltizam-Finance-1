# خطة دفعة P3: تعدد العملات وأسعار الصرف

## الهدف

تهدف P3 إلى نقل «التزام» من افتراض عملة واحدة إلى نموذج مالي يدعم **العملة الأصلية للحركة** و**العملة الأساسية للحساب** و**سعر صرف مؤرخ قابل للتدقيق**، من دون تحويل صامت أو فقدان للمبلغ الأصلي.

سيُستخدم رمز العملة الأبجدي المكوّن من ثلاثة أحرف وفق ISO 4217، مع حفظ عدد الوحدات العشرية لكل عملة بدلاً من افتراض منزلتين لجميع العملات. توضح ISO أن رموز العملات الأبجدية والرقمية تساعد على تقليل الالتباس، وأن الوحدات الصغرى قد تقسم العملة إلى 100 أو 1000 أو غير ذلك [1]. وتوضح قائمة الوحدات المنشورة أن OMR يستخدم 3 منازل عشرية، بينما USD وSAR يستخدمان منزلتين، مع وجود عملات بلا منازل عشرية [2].

> القرار الأساسي: لا يتم تمثيل المبلغ المالي باستخدام `double` كمصدر حقيقة. يُحفظ المبلغ بوحدة صغرى صحيحة أو `numeric` دقيق، ويظل الحقل القديم متاحاً مؤقتاً للتوافق أثناء الترحيل فقط.

## نطاق الإصدار الأول من P3

يتضمن الإصدار الأول سجل العملات، عملة كل محفظة، العملة الأصلية لكل حركة، جدول أسعار صرف مؤرخة، حفظ القيمة المحوّلة عند الحاجة، أدوات إدارة الأسعار، واختبارات الترحيل والتزامن. لا يتضمن الإصدار الأول تداولاً آلياً أو تنفيذ تحويلات حقيقية أو ربطاً مصرفياً يختار سعر الصرف دون موافقة واضحة.

| المجال | داخل P3 | خارج الإصدار الأول |
|---|---|---|
| العملات | ISO code، الاسم، الرمز، الوحدات العشرية، حالة التفعيل | إنشاء عملة مخصصة بلا مصدر موثق |
| المحافظ | عملة ثابتة لكل محفظة | تغيير عملة محفظة تحتوي حركات دون عملية تحويل صريحة |
| المعاملات | مبلغ أصلي، عملة أصلية، مبلغ أساسي اختياري، سعر صرف مؤرخ | استبدال المبلغ الأصلي بالقيمة المحوّلة |
| أسعار الصرف | manual وprovider، effectiveAt، مصدر، دقة عالية | اعتبار سعر ECB المرجعي سعر تنفيذ تجاري تلقائياً |
| التقارير | عرض العملة الأصلية والأساسية والفرق | تحويل كل التاريخ القديم قبل قياس المطابقة |
| الاستيراد | قراءة `currencyCode` وحقول التحويل عند وجودها | استيراد ملف متعدد العملات بلا عملة محددة |

## النموذج المقترح للبيانات

### جدول العملات `currencies`

| الحقل | النوع المقترح | الغرض |
|---|---|---|
| `code` | `CHAR(3)` | المفتاح الأبجدي مثل `OMR`, `USD`, `SAR` |
| `numericCode` | `CHAR(3)` | الرمز الرقمي ISO عند توفره |
| `nameAr` | `TEXT` | الاسم العربي |
| `nameEn` | `TEXT` | الاسم الإنجليزي |
| `minorUnit` | `SMALLINT` | عدد المنازل العشرية المعتمدة للعرض والتطبيع |
| `symbol` | `TEXT` | رمز العرض فقط، وليس مصدراً للحساب |
| `isActive` | `BOOLEAN` | منع العملات القديمة من الاستخدام الجديد دون حذف التاريخ |
| `source` | `TEXT` | ISO أو مصدر داخلي موثق |
| `updatedAt` | `INTEGER` | آخر تحديث للبيانات الوصفية |

يجب أن تبدأ القائمة على الأقل بـ `OMR`, `SAR`, `AED`, `USD`, و`EUR`، ثم توسع تدريجياً. لا ينبغي نسخ قائمة تجارية كاملة داخل الكود إذا كان مصدر البيانات سيصبح قابلاً للتحديث؛ تُحفظ نسخة seed موثقة مع migration.

### جدول أسعار الصرف `exchange_rates`

| الحقل | النوع المقترح | الغرض |
|---|---|---|
| `id` | `SERIAL` | معرف السعر |
| `baseCurrencyCode` | `CHAR(3)` | العملة التي يبدأ منها التحويل |
| `quoteCurrencyCode` | `CHAR(3)` | العملة الناتجة |
| `rate` | `NUMERIC(30,16)` | عدد وحدات quote لكل وحدة base |
| `effectiveAt` | `INTEGER` | وقت صلاحية السعر، لا وقت الإدخال فقط |
| `source` | `TEXT` | manual أو provider أو import |
| `provider` | `TEXT` | اسم مزود السعر عند وجوده |
| `sourceReference` | `TEXT` | رابط أو معرّف المصدر دون سر |
| `isManual` | `BOOLEAN` | تمييز السعر اليدوي |
| `createdAt` | `INTEGER` | وقت الحفظ |
| `createdByUserId` | `INTEGER` | المستخدم الذي أضاف السعر يدوياً عند الحاجة |

يجب فرض فهرس على الزوج والتاريخ، ومنع تكرار السعر لنفس الزوج ونفس لحظة الصلاحية والمصدر. إذا كانت العلاقة العكسية مطلوبة، يجب تخزينها أو اشتقاقها بدقة مع توثيق اتجاه السعر، لا الاعتماد على قلب الرقم بشكل تقريبي.

### تحديث المحافظ والحركات والـ ledger

تضاف الحقول التالية تدريجياً:

| الكيان | الحقول الجديدة | قاعدة الترحيل |
|---|---|---|
| `wallets` | `currencyCode` | جميع المحافظ القديمة تبدأ بـ `OMR` دون تغيير الرصيد |
| `transactions` | `currencyCode`, `amountMinor`, `amountScale`, `baseCurrencyCode`, `baseAmountMinor`, `exchangeRateId`, `exchangeRate` | تُعامل كل الحركات القديمة كـ OMR، وتُحفظ القيمة القديمة للمقارنة |
| `ledgerEntries` | `currencyCode`, `amountMinor`, `amountScale`, `baseCurrencyCode`, `baseAmountMinor`, `exchangeRateId` | يُرحّل مبلغ OMR القديم إلى وحدته الصغرى 1000 دون إعادة تسعير |
| `monthlyBudgets` | `currencyCode`, `amountMinor` | تُرحّل الميزانيات القديمة إلى OMR فقط |
| `bankEmailEvents` | `currencyCode`, `balanceAfterCurrencyCode` | لا يُفترض رمز العملة من نص الرسالة بعد التحليل؛ يجب حفظ نتيجة parser صراحة |

يظل `amount` و`balance` القديمان متاحين كحقول توافق أو cache في أول إصدار. لا يُسمح لأي مسار جديد بإنشاء حركة بلا `currencyCode`، ولا يُسمح بتعديل العملة الأصلية لحركة موجودة؛ التصحيح يكون بحركة عكسية.

## قواعد الحساب والتحويل

يستخدم النظام الاتجاه التالي بشكل ثابت:

```text
convertedAmount = originalAmount × rate(base → quote)
```

يجب حفظ `rate` والزوج والوقت المستخدم، وليس إعادة حساب القيمة القديمة من سعر حالي. عند العرض، يوضح التطبيق دائماً المبلغ الأصلي، العملة الأصلية، والقيمة الأساسية إن كانت محفوظة.

إذا لم يوجد سعر صالح في لحظة الحركة، فالسلوك الافتراضي هو **رفض الحفظ مع رسالة واضحة** أو حفظ الحركة بالعملة الأصلية فقط عندما تكون المحفظة بنفس العملة. لا يُسمح باستخدام آخر سعر معروف بصمت. يمكن توفير خيار يدوي باسم «استخدم هذا السعر» مع تسجيل السبب.

أسعار ECB المرجعية مفيدة كمصدر بيانات مرجعي، لكنها تُنشر عادة في أيام العمل حوالي 16:00 بتوقيت وسط أوروبا، وتوضح الجهة نفسها أنها لأغراض معلوماتية وأن استخدامها للمعاملات غير مستحسن [3]. لذلك سيكون مزود السعر المرجعي في P3 منفصلاً عن سعر التنفيذ اليدوي أو السعر البنكي المستخدم في حركة حقيقية.

## مهام P3 البرمجية

| المعرّف | المهمة | الأولوية | معيار الإنجاز |
|---|---|---:|---|
| P3-CUR-01 | إنشاء جدول العملات وseed للعملات الأساسية | حرجة | كل رمز صالح وله `minorUnit` معروف |
| P3-CUR-02 | إضافة `currencyCode` للمحافظ والميزانيات | حرجة | migration آمنة، وكل القديم OMR |
| P3-CUR-03 | إضافة `amountMinor` وحقول القيمة الأساسية للحركات | حرجة | لا فقد للمبلغ الأصلي، وتقرير فروقات بعد الترحيل |
| P3-FX-01 | إنشاء جدول أسعار الصرف والفهارس | حرجة | اتجاه السعر وتاريخ الصلاحية واضحان |
| P3-FX-02 | بناء خدمة اختيار السعر المؤرخ | حرجة | تختار السعر الصالح الأقرب زمنياً ضمن سياسة معلنة |
| P3-FX-03 | إضافة إدخال السعر اليدوي وسجل التدقيق | عالية | كل تعديل مسجل بفاعل وسبب ووقت |
| P3-FX-04 | إضافة مستورد مزود مرجعي read-only | متوسطة | لا يكتب أسعار تنفيذ دون موافقة |
| P3-TX-01 | ترقية إنشاء المعاملة والتحويل | حرجة | رفض العملة المفقودة أو الزوج غير المسعّر |
| P3-TX-02 | ترقية استيراد P2 | عالية | يدعم الحقول الجديدة ويرفض الملف الغامض |
| P3-TX-03 | ترقية العكس والتعديل | عالية | الحركة العكسية تستخدم نفس العملة والسعر التاريخي |
| P3-RPT-01 | عرض الأصل والأساسي في التقارير | عالية | لا تختلط المجاميع بين العملات |
| P3-RPT-02 | إضافة تقرير فروقات العملة | متوسطة | يظهر أثر سعر الصرف والتحويلات بوضوح |
| P3-UX-01 | شاشة إعداد العملة الأساسية | عالية | تغيير العرض لا يغير السجلات الأصلية |
| P3-UX-02 | مؤشرات العملة في المحافظ والمعاملات | عالية | رمز العملة ظاهر بجانب كل مبلغ |
| P3-QA-01 | اختبارات seed وminor units والتحويل | حرجة | تغطية OMR/USD/JPY وعملة ثلاثية المنازل |
| P3-QA-02 | اختبارات التزامن والتسعير المؤرخ | حرجة | نفس الحركة لا تحصل على سعرين متعارضين |
| P3-QA-03 | اختبار migration على نسخة staging | حرجة | تطابق أرصدة OMR قبل وبعد الترحيل |

## خطة الترحيل

يُنفذ الترحيل على مراحل منفصلة حتى لا تتغير الأرقام دفعة واحدة:

1. إنشاء العملات وseed، ثم إضافة أعمدة nullable إلى الجداول الحالية.
2. فحص أي مبالغ غير صالحة أو أرصدة غير رقمية وتسجيلها قبل التعديل.
3. تعيين `OMR` لكل المحافظ والحركات والميزانيات القديمة.
4. تحويل قيمة OMR إلى `amountMinor` باستخدام scale 3، مع حفظ القيمة القديمة للمقارنة.
5. إنشاء تقرير reconciliation يطابق مجموع ledger والرصيد الظاهر قبل وبعد الترحيل.
6. تفعيل الكتابات الجديدة متعددة العملات خلف feature flag.
7. تفعيل القراءة متعددة العملات بعد اجتياز staging والاختبارات التكاملية.
8. إبقاء الحقول القديمة للقراءة الاحتياطية خلال إصدار واحد على الأقل قبل التفكير في إزالتها.

## واجهات API المقترحة

```text
GET    /api/currencies
GET    /api/exchange-rates?base=OMR&quote=USD&at=...
POST   /api/exchange-rates
PATCH  /api/exchange-rates/:id
GET    /api/settings/currency
PUT    /api/settings/currency
POST   /api/transactions/quote
POST   /api/transactions
GET    /api/reports/summary?currency=OMR
GET    /api/reports/fx-impact
```

`POST /api/transactions/quote` يعرض السعر والقيمة المحوّلة قبل الحفظ، لكنه لا ينشئ حركة. عند الحفظ يجب إرسال `quoteId` أو `exchangeRateId` حتى لا يتغير السعر بين المعاينة والتأكيد.

## الاختبارات المطلوبة

ينبغي اختبار OMR بثلاث منازل عشرية، USD وSAR بمنزلتين، JPY بلا منازل، والتحقق من التقريب عند التحويل في الاتجاهين. كما يجب اختبار أن 10 OMR لا تصبح 10 USD بسبب غياب السعر، وأن إعادة عرض حركة قديمة لا تستخدم سعر اليوم، وأن عكس حركة بعملة أجنبية لا يغيّر عملتها الأصلية.

يجب أن تشمل اختبارات PostgreSQL migration مستخدمين بمحافظ OMR، ثم إضافة USD، وإنشاء حركة بسعر مؤرخ، ثم تشغيل إعادة المحاولة والحذف والعكس والتصدير والاستيراد. يجب أن تفشل الاختبارات إذا أصبح مجموع wallet cache مختلفاً عن ledger بعد الترحيل.

## المخاطر وقرارات الحماية

أكبر خطر هو تحويل العملة الأصلية بدلاً من حفظها، أو استخدام سعر حالي لإعادة بناء تاريخ قديم، أو جمع مبالغ من عملات مختلفة في بطاقة واحدة. لذلك يجب أن يحمل كل aggregate عملة أو يعرض «متعدد العملات» ولا يجمع القيم إلا بعد تحويل مؤرخ.

الخطر الثاني هو اعتبار سعر مرجعي خارجي سعر تنفيذ. يُحفظ مصدر السعر وحالته، ويُعرض للمستخدم ما إذا كان السعر يدوياً أو مرجعياً. والخطر الثالث هو تغيير عملة المحفظة بعد وجود حركات؛ يُمنع ذلك إلا بعملية تحويل صريحة أو إنشاء محفظة جديدة.

## قرار بدء التنفيذ

يبدأ P3 فعلياً بالمهام `P3-CUR-01`, `P3-CUR-02`, و`P3-FX-01`، ثم اختبارات الترحيل قبل تعديل إنشاء المعاملات. لا يبدأ استيراد أسعار خارجية أو تحويل التقارير حتى يثبت أن OMR القديم يطابق ledger بعد migration.
